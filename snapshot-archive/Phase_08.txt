================================================================================
PHASE 8: INVOICING, PAYMENTS & FINANCIAL DOCUMENTS - CODE & DATABASE LEVEL ANALYSIS
================================================================================

This document provides deep code-level and database schema analysis
of the financial document modules in the procurement cycle, scraped
from the live application.

---
1. APPLICATION ARCHITECTURE (CODE LEVEL)
---

1.1 Technology Stack
  - Backend: PHP (server-rendered, no REST framework)
  - Frontend: jQuery + Bootstrap 4 + DataTables + Select2
  - Database: MySQL (inferred from PHP/LAMP stack)
  - Session: PHP sessions (PHPSESSID cookie)
  - Routing: Single entry point (index.php) with option-based routing

1.2 Module Overview
  Five financial document modules form the accounting layer:
  - purchase_invoices (COM_INSERT_PURCHASE_INVOICES)  Table: purchase_invoices
  - payments         (COM_INSERT_PAYMENTS)               Table: payments
  - debit_notes      (COM_INSERT_DEBIT_NOTES)            Table: debit_notes
  - supplier_bills   (COM_INSERT_SUPPLIER_BILLS)         Table: supplier_bills
  - credit_notes     (COM_INSERT_CREDIT_NOTES)           Table: credit_notes

  All use has_line_items: False (line items loaded via AJAX).

1.3 Document Lifecycle Chain

  Supplier Bill (external) --> Purchase Invoice (internal record)
  Purchase Invoice --> Payment (settlement)
  Purchase Invoice --> Debit Note (return/adjustment)
  Debit Note --> Credit Note (reversal of debit)

  Inter-document reference chain:
  PO (purchase_orders) --> PI (purchase_invoices) via ref_id
  GRN (goods_receipt_notes) --> PI via ref_no
  SB (supplier_bills) --> PI (inferred, supplier_bill_ref_id)
  PI (purchase_invoices) --> Payment via ref_id

1.4 Routing Convention
  COM_LIST_PURCHASE_INVOICES  -> List/view
  COM_INSERT_PURCHASE_INVOICES -> Insert
  COM_LIST_PAYMENTS            -> List/view
  COM_INSERT_PAYMENTS          -> Insert
  COM_LIST_DEBIT_NOTES         -> List/view
  COM_INSERT_DEBIT_NOTES       -> Insert
  COM_LIST_SUPPLIER_BILLS      -> List/view
  COM_INSERT_SUPPLIER_BILLS    -> Insert
  COM_LIST_CREDIT_NOTES        -> List/view
  COM_INSERT_CREDIT_NOTES      -> Insert

2.1 Table: purchase_invoices (Header)

    id INT AUTO_INCREMENT PRIMARY KEY,
    ref_type VARCHAR(50),
      -- Hidden field, empty value scraped
      -- Likely: 'purchase_orders' (PI created from PO)
    transaction_number VARCHAR(50),
    transaction_date DATE,
    opex_cpex TINYINT DEFAULT 0,
    ref_date DATE,

      -- Links PI to the goods receipt

      -- 'RURAL REQUIREMENT' | 'URBAN REQUIREMENT'
      -- 'HO REQUIREMENTS' | 'PROJECT REQUIREMENTS'
    originator VARCHAR(50) DEFAULT 'ADMIN',
    cost_center_id INT DEFAULT 0,
      -- FK to cost_centers.id
    party_id INT DEFAULT 0,
      -- FK to vendors.id
    payment_terms VARCHAR(50),
    transaction_location_id INT DEFAULT 0,
      -- Hidden: delivery/receiving location
    transaction_warehouse_id INT DEFAULT 0,
      -- Hidden: receiving warehouse
    originator_state_id INT DEFAULT 0,
      -- Hidden: buyer's state (GST)
    supplier_state_id INT DEFAULT 0,
      -- Hidden: vendor's state (GST)
    total_amount DECIMAL(15,2) DEFAULT 0,
      -- Inferred: sum of line item totals
    gst_total DECIMAL(15,2) DEFAULT 0,
      -- Inferred: total GST amount
    grand_total DECIMAL(15,2) DEFAULT 0,
      -- Inferred: total_amount + gst_total
    status TINYINT DEFAULT 0,
    created_by INT DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP

  Key fields unique to purchase_invoices:
  - ref_type: Hidden, determines source document type
  - ref_date: Date from reference PO
  - doc_ref_no/doc_ref_date: External vendor invoice reference
  - ref_id: FK to purchase_orders (the PO being invoiced)
  - ref_no: FK to goods_receipt_notes (GRN being invoiced)

4. BUSINESS RULES
---

4.1 Purchase Invoice Creation
  Purchase invoices are created against approved purchase orders:
  - ref_id selects the PO being invoiced
  - ref_no selects the GRN (Goods Receipt Note) for quantity validation
  - doc_ref_no/doc_ref_date record the vendor's own invoice reference
  - Line items are copied from PO with prices locked
  - Quantities may be adjusted based on actual GRN quantities
  - Two-level reference: PO (contract) and GRN (receipt)

4.2 Supplier Bill vs Purchase Invoice
  Two distinct concepts exist:
  - Supplier Bills: External vendor bills recorded for AP tracking
    Has due_date, tax_state, no GRN reference
  - Purchase Invoices: Internal procurement invoices linked to PO/GRN
    Has GRN reference, no due_date
  The supplier_bill is a simpler record for accounts payable.
  The purchase_invoice is a full procurement document with line items.
  A supplier bill may be converted to a purchase invoice later.

4.3 Debit Note Flow
  Debit notes are created when:
  - Goods are returned to the vendor
  - Invoice amount needs reduction (price dispute)
  - Quality issues result in partial rejection
  Linked to the original purchase_invoice via ref_id.
  place_of_supply is plain text (carried from PI, not re-calculated).

4.4 Credit Note Flow
  Credit notes reverse or adjust debit notes:
  - Created when a debit note is cancelled/reversed
  - Or when returned goods are re-accepted
  - Linked to debit_note via ref_id (inferred)
  Simplest form: no ref_type, no state fields.

4.5 Payment Processing
  The payments module is minimal in its form (only date range).
  Actual payment creation likely occurs from:
  - PI detail page ("Record Payment" action button)
  - Supplier Bill detail page ("Record Payment" action button)
  Payment creation references the source document (PI or SB)
  and the vendor's bank account.

4.6 Payment Terms
  Financial documents support standardized payment terms:
  NET +7 DAYS, NET +15 DAYS, NET +30 DAYS,
  NET +45 DAYS, NET +60 DAYS, NET +90 DAYS
  These appear on debit_notes, supplier_bills, and credit_notes.
  The due_date on supplier_bills is calculated based on
  payment_terms + transaction_date.

4.7 GST Handling Across Financial Documents
  - purchase_invoices: Uses originator_state_id + supplier_state_id
    (same as quotation) for CGST/SGST vs IGST determination
  - supplier_bills: Uses tax_state dropdown (FK to states table)
    instead of hidden state fields
  - debit_notes: place_of_supply is plain text, no state IDs
    GST likely pre-calculated and stored in line items
  - credit_notes: Same as debit_notes, plain text place_of_supply

4.8 OPEX/CAPEX Consistency
  All financial documents carry opex_cpex inherited from
  the originating purchase order. This classification is
  immutable downstream and drives financial reporting.

4.9 Three-Way Matching (Inferred)
  The purchase_invoice form has both ref_id (PO) and ref_no (GRN),
  enabling three-way matching:
  1. PO quantity and price (contract)
  2. GRN quantity (actual receipt)
  3. Vendor invoice quantity and price (billing)
  Discrepancies trigger variance alerts based on the
  price_variance and qty_variance settings on item_categories.

4.10 Type Classification
  All financial documents carry the type field:
  RURAL/URBAN/HO/PROJECT REQUIREMENTS
  Inherited through the PO chain. Enables segmented
  financial reporting by organizational function.

  The getStockBalanceAvailability() function checks inventory
  before status changes on delivery_orders and sales_invoices.
  While not directly triggered for purchase_invoices, the pattern
  applies to the sales-side equivalents. For procurement:
  - PI creation may trigger GRN quantity validation
  - PO status change to 'Received' updates stock levels
  - The check ensures stock doesn't go negative unless
    item.negative_stock = Y

6.3 Decimal Number Validation (custom.js)
  $('body').on('input', '.decimalnumberallowe', function() {
    let value = $(this).val();
    let sanitized = value.replace(/[^0-9.]/g, '');
    sanitized = sanitized.replace(/(\..*?)\..*/g, '$1');
    $(this).val(sanitized);
  });

  Financial amount fields use the .decimalnumberallowe class.
  This client-side validator:
  - Removes all non-numeric characters except decimal point
  - Ensures only one decimal point is allowed
  - Does NOT enforce decimal places (server handles that)
  Applied to unit_price, quantity, gst_amount, total_amount fields.

6.4 Dynamic Workflow with Mandatory Check (custom.js)
  Both submitDynamicWorkflow() and submitDynamicWorkflowPopUp()
  check for a page-specific checkMandatoryArray() function.
  On financial document pages, this function likely validates:
  - Line items exist (at least one item)
  - Amounts are positive
  - GST calculations are complete
  - Required attachments (vendor invoice copy) are uploaded

6.5 Error Response Handling (custom.js)
  function dynamicErrorShow(respon) {
    if (respon.status == "fail") {
      Swal.fire({
        icon: 'error',
        title: 'Oops...',
        text: respon.message
      });
      return {result: "1", LASTID: respon.message};
    } else {
      return {result: "0", LASTID: respon.LASTID};
    }
  }

  Server responses on form submit use this standardized format.
  status='fail' triggers error display. LASTID returns the
  newly created record ID on success. Financial document
  creation may return additional data (calculated totals).
