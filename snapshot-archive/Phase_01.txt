1. Executive Summary
This document presents the first phase of a comprehensive reverse engineering effort for a web-based Procurement Management System. The system is a full-featured enterprise application designed to manage the complete procure-to-pay lifecycle, from purchase requisitions through quotations, purchase orders, invoicing, payments, and inventory gate pass management. The platform follows a modular architecture built on PHP with a jQuery-based front-end, using a single-page application pattern where all module views are rendered within a common dashboard shell.
The reverse engineering initiative is organized into ten distinct phases, each producing a standalone deliverable document. This first phase establishes the foundational understanding of the application by documenting its overall architecture, technology stack, module inventory, navigation paradigm, generic framework patterns, and URL routing conventions. Subsequent phases will progressively drill into each module, documenting entity structures, API endpoints, business rules, and inter-module relationships in granular detail.
The system has been accessed, navigated, and analyzed through automated browser interaction with valid administrative credentials. Every module, form, list page, and configuration screen has been inspected to extract field-level metadata, form actions, hidden system fields, and UI patterns. The findings in this document are based on direct observation of the running system rather than inferred from source code.
2. Technology Stack
2.1 Back-End Technologies
The application server is built on PHP, evidenced by the file extension ".php" in all URL endpoints and the presence of PHP session management headers. The routing mechanism uses a single entry point pattern where the file “index.php” serves as the central dispatcher. A query parameter named “option” determines which module controller or view is loaded, following the convention COM_[ACTION]_[MODULE_NAME] (for example, COM_LIST_QUOTATIONS loads the quotation listing view, while COM_INSERT_QUOTATIONS loads the quotation creation form). This convention is consistently applied across all modules in the system.
AJAX interactions are handled through a dedicated endpoint at “ajax.php”, which accepts POST requests with a “page” parameter to route to different server-side handlers. The system employs jQuery 2.1.3 for front-end AJAX calls, Underscore.js 1.8.3 for templating utilities, and Moment.js 2.10.6 for date manipulation. The data table listings use a server-side processing pattern where the client sends start, length, and status parameters, and the server returns JSON with recordsTotal, recordsFiltered, and a data array.
2.2 Front-End Technologies
The front-end leverages a combination of jQuery-based components and Bootstrap-style layout patterns. The user interface uses Font Awesome icons for visual elements throughout the sidebar, action buttons, and status indicators. The sidebar navigation employs collapsible menu groups with click-based toggle functionality for sub-menu expansion. Date picker components are integrated for all date fields, defaulting to the DD-MM-YYYY format as configured in the system settings.
The dashboard implements a multi-panel layout with real-time notification counters, quick-access widget cards, and tabbed content areas. The notification system uses AJAX polling to check for new action items, informational alerts, and system logs. Modal dialogs (using Bootstrap modal patterns) are employed for pop-up forms, confirmations, and detail views. The data grid component supports column filtering, pagination, status-based tab filtering (Active/Inactive/All), full-text search, and export/import functionality.
2.3 Session and Security
Authentication is managed through a dedicated “login.php” page that implements captcha-based protection against automated login attempts. The login form captures username, password, and a captcha code. Upon successful authentication, PHP session management maintains the user state across page navigations. The system captures client IP address and browser user-agent during login for audit purposes. The hidden “subdomain” field in the login form suggests a multi-tenant architecture where each deployment operates under a subdomain identifier.
The login form also includes embedded signup and forgot-password forms on the same page, toggled via client-side JavaScript. The signup form captures name, email, and password, while the forgot-password form accepts an email address for password recovery initiation. Session timeout has been observed during extended analysis periods, requiring re-authentication, which indicates a server-configured session expiration policy.

4. Navigation Architecture
4.1 Sidebar Navigation Structure
The application uses a left sidebar navigation pattern with collapsible menu groups. The sidebar contains two primary menu groups for data entry: “Masters” and “New”. The Masters menu expands to reveal all master data management modules (Divisions, Departments, Locations, Cost Center Types, Cost Centres, Item Categories, Items Type, Costing Type, UOM, Items, HSN Code, Currencies, Vendors, Invite Vendors, Users, Invite Users). The “New” menu provides quick access to transaction creation forms (Generate Quotations from Requisitions, Quotations, Generate Purchase Orders from Requisitions, Generate Purchase Orders from Quotations, Purchase Orders, Purchase Invoices, Payments, Debit Note, Supplier Bills, RGP, NRGP, Credit Note).
The top header bar provides quick-access links including Profile, My Messages, Configuration, and a Logout option. A notification bell icon displays an unread count badge and expands into a three-tab panel (Action, Information, Logs) showing real-time system notifications. The “Modules” button in the sidebar appears to provide a module management or configuration view. The user’s avatar and role label (e.g., “ADMIN”) are displayed at the bottom of the sidebar, along with a toggle to switch between Admin and Employee access modes.
4.2 URL Routing Convention
All application pages are accessed through a consistent URL pattern: “https://[domain]/index.php?option=[OPTION_CONSTANT]”. The option parameter follows the naming convention COM_[ACTION]_[MODULE], where ACTION is either LIST (for listing/views), INSERT (for create forms), or VIEW (for read-only detail views). Some pages include additional query parameters such as “Rid” (encoded record ID for edit mode), “table” (for generic list operations), “code” (for filtered code lists like COSTCENTERTYPE or INVCOST), and “clone” (for generate-from operations).
The login page is a separate PHP file at “/login.php”, while all authenticated pages route through “/index.php”. AJAX data operations target “/ajax.php” with POST parameters. The system also uses “/views/” directory for server-side rendered partial views loaded dynamically via AJAX (for example, “views/new_from.php” for popup forms, “views/custom_list_notification_popup.php” for notification panels, and “views/custom_change_admin_to_employees.php” for admin/employee mode switching).
5. Generic Framework Patterns
5.1 Common Master Module Form Architecture
A significant portion of the system’s modules follow a generic, code-driven form architecture. Modules such as Divisions, Departments, Locations, Cost Centers, Item Types, Unit of Measurements, HSN/SAC Codes, and Currencies all share a common set of hidden system fields that drive the form’s behavior. This generic framework injects the following hidden fields into every form: in_date_pic (date field metadata), in_currency_fileds (currency field metadata), in_phone_fileds (phone field metadata), mandatory_str (comma-separated list of mandatory field names for client-side validation), add_mandatory_str (additional mandatory fields for edit mode), notification_users (comma-separated user IDs to notify on create), notification_message (template message for notifications), dis_label (URL-encoded JSON mapping field names to display labels for duplicate detection messages), image (the image upload field name), duplicate_table_name (the database table to check for duplicate entries), insert_page_names (the option constant for the insert page), and list_page_names (the option constant for redirect after save).
All generic master module forms include a “from_date” field (always marked as required) and a “to_date” field, implementing an effective dating pattern that allows records to have validity periods. The save action is triggered by a hidden “submit” field with value “Add” for new records or “Update” for edits. Two save buttons are provided: “Save & Exit” (returns to list page) and “Save & Continue” (stays on the form for additional entries). A “Cancel” button navigates back to the list page. This common framework dramatically reduces development effort for new master modules and ensures consistent behavior across the system.
5.2 Transaction Module Form Architecture
Transaction modules (Requisitions, Quotations, Purchase Orders, Purchase Invoices, Supplier Bills, Returnable Gate Passes, Non-Returnable Gate Passes) share a more complex common form pattern consisting of two forms per page. The first form (GET method) serves as a search/filter bar with fields for item name/SKU search, item type, category, location, warehouse, vendor, and customer selection. This allows users to quickly find and add items to the transaction line grid from the same page.
The second form (POST method) is the main transaction entry form with three sections: (1) a header section with transaction metadata fields such as transaction number (auto-generated), transaction date, reference type, OPEX/CAPEX classification, originator, cost center, party (vendor/customer) selection, payment terms, place of supply, currency selection with exchange rate, document references, and due dates; (2) a dynamic item line grid with per-row fields for product selection, product name, UOM, customer description, quantity, unit price, discount, required date, and hidden fields for tax calculations and inventory history; and (3) a footer section with notes, printing notes, discount configuration (amount or percentage), tax type selection, additional charge handling, and computed totals (subtotal, discount amount, tax amounts, shipping charges, and grand total).
The footer also includes “Amount Paid” and “Amount Due” fields that are automatically calculated. Hidden system fields track the transaction status (status_values), backdate validation limit, mandatory field configuration (mandatory_array encoded as JSON), company and location context, user context, amendment state, and all computed financial totals. This architecture enables the system to handle complex procurement calculations while maintaining a consistent user experience across all transaction types.
5.3 List Page Architecture
All list pages share a common architecture with the following components: a status filter bar (typically radio buttons for Active, Inactive, and All states, or for vendor invitations: All, Active, In-Progress, Invited), import and export action links, a “New [Entity]” creation link, a column visibility toggle (allowing users to show/hide table columns), a full-text search box, a pagination control with configurable page size (default 20 records per page), and a server-side processed data grid that loads data via AJAX calls to “ajax.php?page=getlistdata&option=[OPTION]&status=[status]&start=[offset]&length=[pageSize]”. The data grid supports row-level actions accessible through action buttons or dropdowns, and a “Back” navigation link.
6. System Configuration Overview
The Configuration module (accessible via the top header “Config” link) provides centralized system settings organized into several sections. The Company Information section captures the organization name, display logo, license number, tax number, GST number, CIN number, PAN number, phone, and fax. The Address section includes billing and contact addresses. Regional Settings include timezone (default: Asia/Kolkata), date format (default: DD-MM-YYYY), date separator (default: hyphen), percentage position, and number format (default: 1.2). Financial Settings include default currency, default language, KPI mode (enabled/disabled), default payment mode, default cash account, default tax account, and various clearing and payable accounts for TDS and TCS handling. Document Settings include invoice prefix and postfix for auto-numbering, application module selection, copyright text, and default country. The configuration also stores effective dating (from_date and to_date) and uses the standard notification and duplicate-check hidden fields.
7. Dashboard Widgets and Layout
The dashboard (landing page after login) presents a multi-panel layout organized into several widget areas. The left sidebar contains the main navigation menus as described in Section 4.1. The main content area displays: (1) a “Quotations” summary widget with draft/active/in-process/approved tab counts and a “View all” link for each status; (2) an “Announcements” widget displaying system announcements; (3) a “Holidays” widget showing upcoming holidays; (4) a “Search vendor/customer” quick-search widget with radio toggles for vendor vs. customer search; (5) tabbed panels for “Approved Requisitions”, “Item Categories”, “Locations”, and “Cost Centers” showing quick counts; (6) a “Self” tab showing documents created by the current user, and an “Action” tab showing documents requiring the user’s action with sub-counts for different action types.
The notification panel (accessible via the bell icon) provides a three-tab view: Action (items requiring user action), Information (informational notices), and Logs (system activity log). Each notification type supports individual dismissal via AJAX calls to “ajax.php?page=closenotificationinfo” and bulk dismissal via “ajax.php?page=closeallnotifications”. The dashboard also features a time tracker widget with start/pause functionality, suggesting an integrated time-tracking capability that logs work sessions via AJAX.
8. Key Architectural Observations
Several important architectural patterns emerge from this analysis. First, the system employs an effective dating pattern universally: every entity supports from_date and to_date fields, enabling temporal data management and historical record tracking. Second, the generic framework pattern allows rapid module development by providing a template-driven approach for both master data and transaction processing modules. Third, the system uses a notification-driven workflow where create, update, and status change events trigger notifications to configured users via the notification_users and notification_message hidden fields. Fourth, the multi-tenant architecture is evidenced by the subdomain-based login mechanism and company-scoped configuration.
Fifth, the transaction modules implement a progressive document flow: Requisitions lead to Quotations (or directly to Purchase Orders), which lead to Purchase Invoices, which lead to Payments. Each transition can optionally reference the source document through the ref_type and ref_id fields. Sixth, the system includes comprehensive tax handling infrastructure with GST, TDS, and TCS support built into both master data (HSN codes, vendor GST details) and transaction processing (tax calculation, tax accounts). Seventh, the inventory management layer tracks stock through warehouse assignments, quantity levels (minimum, danger, maximum), reorder quantities, and gate pass movements for both returnable and non-returnable items.
