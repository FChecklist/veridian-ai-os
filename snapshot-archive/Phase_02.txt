1. Authentication System
The authentication system serves as the primary gateway into the Procurement Management System, enforcing identity verification before granting access to any application modules. It is designed around a traditional server-side session model with multi-tenant awareness, ensuring that each tenant organization is securely isolated from every other tenant within the shared deployment. The login interface is rendered through login.php and incorporates multiple layers of validation including client-side form checks, server-side credential verification, and a captcha-based challenge to protect against automated brute-force attacks. This layered approach balances security requirements with user convenience, minimizing friction during legitimate authentication attempts while raising the barrier for unauthorized access vectors.
1.1 Login Page Structure
The login page is implemented as a single-file PHP script (login.php) that handles both the initial display of the login form and the subsequent authentication request processing. The page follows a clean, centered layout pattern typical of enterprise SaaS applications, presenting the user with a compact form that requests only the essential credentials needed for authentication. Upon rendering, the page also initializes the captcha challenge and sets up the necessary session variables that will be referenced during form validation on the server side. The form action posts back to the same login.php endpoint, enabling a streamlined request-response cycle without requiring client-side routing or additional endpoints for the authentication handshake.
1.1.1 Visible Form Fields
The login form presents three visible input fields to the user, each serving a distinct purpose in the authentication flow. The chrUserName field is a standard text input that captures the user's unique login identifier and is marked as required by both HTML5 validation and server-side checks. The chrPassword field is a password-type input that masks the entered characters, preventing shoulder-surfing attacks in shared or public environments, and is likewise marked as required. The captcha field is a text input where the user must transcribe the characters displayed in the captcha image; this field is also required and must exactly match the server-generated challenge string stored in the user's session. All three fields are validated in sequence: missing required fields trigger immediate client-side validation errors, while the captcha mismatch is reported via error code 6007 from the server.

1.1.2 Hidden Fields
In addition to the visible user-facing inputs, the login form embeds four hidden fields that capture contextual and operational metadata critical to the authentication process. The ip field is populated with the client's IP address, typically extracted from the server request headers (REMOTE_ADDR or X-Forwarded-For in proxied environments), and is used for audit logging and potential geo-restriction checks. The browser field captures the full User-Agent string from the client's HTTP request, providing a fingerprint that assists in session tracking and anomaly detection when the same account is accessed from different browsers or devices over time. The subdomain field encodes the multi-tenant identifier, allowing the authentication system to route the login attempt to the correct tenant's data partition without requiring the user to manually select their organization. Finally, the submit field with a value of "Login" serves as the form submission trigger and is used by the server to distinguish a legitimate login POST from other potential form submissions to the same endpoint.

1.2 Captcha Mechanism
The captcha mechanism provides a critical defense layer against automated credential stuffing and brute-force login attempts by requiring human intervention in the authentication flow. The captcha image is generated server-side through the endpoint captcha/captcha.php, which dynamically creates a graphical challenge containing a random alphanumeric string. This string is simultaneously stored in the server-side session associated with the current HTTP session identifier, establishing a binding between the visual challenge presented to the user and the expected response held on the server. When the login form is submitted, the value entered in the captcha text field is compared against the session-stored value using a case-sensitive string comparison. If the values do not match, the server returns error code 6007, which triggers a client-side error message instructing the user to retry the captcha challenge. A new captcha image is automatically generated upon each failed attempt, invalidating the previous session value and preventing replay attacks.
The session-bound nature of the captcha validation ensures that the challenge-response pair cannot be transferred between different browser sessions or users. Since the captcha value is stored exclusively in the PHP session and never exposed to the client outside of the rendered image, an attacker cannot programmatically retrieve the expected answer without solving the visual challenge itself. The captcha.php endpoint generates the image using PHP's GD library, applying random rotation, noise lines, and character distortion to increase resistance against optical character recognition (OCR) tools. This approach provides a practical balance between security and usability, as it presents a challenge that is straightforward for human users but computationally expensive for automated scripts to bypass consistently.
1.3 Session Management with Timeout
Upon successful authentication, the system establishes a server-side PHP session that maintains the user's authenticated state across subsequent requests. The session stores critical user context including the user identifier, assigned role, tenant association, and authentication timestamp. Session management employs an idle timeout mechanism that automatically invalidates the session after a configured period of inactivity, requiring the user to re-authenticate to continue. This timeout is enforced by comparing the session's last activity timestamp against the current server time on each request; if the elapsed duration exceeds the configured threshold, the session is destroyed and the user is redirected to the login page with an appropriate expiration message. The timeout value is configurable at the system level, allowing administrators to balance security requirements against usability considerations based on their organization's operational patterns and risk profile.
The session management subsystem also handles concurrent session control, ensuring that a single user account cannot maintain multiple simultaneous sessions unless explicitly permitted by the configuration. When a new login is detected for an account that already has an active session, the system may optionally terminate the previous session, forcing re-authentication on the older client. Session data is stored server-side with the session identifier communicated to the client via an HTTP cookie, following the standard PHP session handling model. All session cookies are configured with the HttpOnly and Secure flags to prevent client-side script access and ensure transmission only over encrypted HTTPS connections. This comprehensive session management approach ensures that authenticated sessions remain protected against hijacking, fixation, and replay attacks throughout their lifecycle.
1.4 Forgot Password Flow
The Forgot Password functionality is integrated directly into the login page, allowing users who have forgotten their credentials to initiate a password reset without navigating to a separate URL. When the user clicks the "Forgot Password" link, the login form is replaced by an email input form on the same page through a JavaScript-driven UI transition. The user is required to enter the email address associated with their account, which the server then validates against the registered user records within the current tenant context. If a matching account is found, the system generates a single-use, time-limited password reset token that is embedded in a secure link sent to the user's registered email address. This email contains instructions and a direct link that, when clicked, redirects the user back to the application where they can set a new password.
The password reset token is designed with a finite expiration window, typically measured in hours, after which it becomes invalid and the user must initiate a new reset request. Each token is also single-use; once it has been consumed to set a new password, it cannot be reused even if it has not yet expired. The system does not disclose whether a given email address exists in its records, responding with a generic success message regardless of whether a reset email was actually sent, thereby preventing user enumeration attacks. After the password is successfully reset, all existing sessions for that user are invalidated, requiring a fresh login with the new credentials. This flow ensures that even if a malicious actor gains access to the reset email, the window of exploitation is limited and the legitimate user is immediately made aware of the session termination.
1.5 Sign Up Flow
The Sign Up flow is presented as a toggleable section on the login page, enabling new users to register for an account without leaving the authentication context. When activated, the form displays three fields: name (a required text input capturing the user's full name), email (a required text input for the user's email address, which also serves as the login identifier), and password (a required password input for setting the initial account credential). The sign-up form validates all three fields on the client side before submission, checking for minimum password length and proper email format. Upon submission, the server performs additional validation including checking for duplicate email addresses within the current tenant and ensuring the password meets the configured complexity requirements.
Depending on the system configuration, newly registered accounts may be placed in a pending approval state, requiring an administrator to review and activate the account before the user can log in. Alternatively, the system may be configured for automatic activation, allowing immediate access upon successful registration. The sign-up process also initializes a default role assignment for the new user, typically a restricted role with limited permissions until an administrator assigns a more appropriate role based on the user's organizational function. This approach ensures that self-registered users cannot immediately access sensitive modules while still providing a frictionless onboarding experience. The registration data is captured within the multi-tenant context identified by the subdomain, ensuring proper organizational isolation from the moment of account creation.
2. User Management Module
The User Management module provides administrators with a comprehensive interface for creating, maintaining, and organizing user accounts within the Procurement Management System. Accessed through the COM_LIST/INSERT_APPLICATION_USERS command, this module serves as the central personnel administration hub, enabling fine-grained control over user identities, their organizational attributes, and their access profiles. The module is designed to support the full user lifecycle from initial creation through ongoing maintenance to eventual deactivation, ensuring that the user directory remains accurate and aligned with the organization's current workforce structure. All user management operations are scoped to the current tenant context, maintaining the multi-tenant isolation that is fundamental to the system's architecture.
2.1 User Creation Fields
The user creation form collects a rich set of attributes that define each user's identity, contact information, and organizational placement within the system. The form is divided into logical field groups that map to different aspects of the user profile. Mandatory fields are enforced at both the client and server layers, ensuring data integrity before the record is persisted to the database. Optional fields allow administrators to provide additional context and contact information that enhances the user's ability to collaborate within the platform. The comprehensive nature of the user record supports downstream features such as organizational reporting, communication routing, and location-based access policies.

The first_name and display_name fields are both marked as required, reflecting the system's need to present meaningful identifiers throughout the interface. The display_name field provides flexibility for users who prefer to be known by a nickname or formal title in the application context, separate from their legal name. The user_email field serves a dual purpose: it acts as the primary communication channel for system notifications and also functions as the login identifier, simplifying the authentication experience by using a familiar, memorable credential. The country_id and location_id fields are populated from reference data tables, enabling administrators to associate users with specific geographic and organizational contexts that may influence their access to region-specific modules, tax calculations, and compliance workflows.
2.2 List Page and Status Filtering
The user list page provides a searchable, filterable directory view of all user accounts within the current tenant, enabling administrators to quickly locate and manage individual users. The page presents user records in a tabular format with columns for key attributes such as display name, email, role, location, and current status. A prominent status filter allows administrators to narrow the view to Active users, Inactive users, or All users, depending on the administrative task at hand. The Active filter is typically the default view, showing only users who currently have the ability to log in and interact with the system. The Inactive filter displays deactivated accounts that may need to be reviewed for reactivation or permanent removal. The All filter provides a complete inventory of the user base regardless of status.
Each row in the user list includes action links for editing the user record, resetting the user's password, and toggling the user's active/inactive status. The list supports pagination for organizations with large user bases, ensuring that the page remains responsive even when managing hundreds or thousands of user accounts. Sorting capabilities allow administrators to order the list by any visible column, facilitating tasks such as alphabetical reviews of the user directory or identifying recently modified accounts. The combination of filtering, sorting, and pagination creates a powerful administrative interface that scales effectively across organizations of varying sizes and complexity.
2.3 User Invitation System
The User Invitation system, accessed through COM_LIST/INSERT_APPLICATION_USER_INVITATIONS, provides an alternative user onboarding pathway that delegates the initial credential setup to the invited user themselves. Rather than an administrator manually creating an account with a temporary password, the invitation flow sends a secure, personalized invitation email to the prospective user containing a unique registration link. When the recipient clicks this link, they are directed to a self-service registration form where they can set their own password and complete their profile information. This approach reduces the administrative overhead associated with manual account provisioning and improves security by ensuring that only the intended recipient can activate the account, since the invitation link is both single-use and time-limited.
The invitation management interface displays a list of all pending, accepted, and expired invitations, giving administrators visibility into the onboarding pipeline. Pending invitations can be resent or revoked by administrators before they expire, providing flexibility when dealing with delayed responses or incorrect email addresses. When an invitation is accepted, the system automatically creates the user record and assigns the role and organizational attributes that were specified when the invitation was originally generated. This seamless transition from invitation to active user account ensures that the user directory remains consistent and that newly onboarded users are immediately productive within their assigned role and organizational context. The invitation system integrates with the notification framework to alert administrators when invitations are accepted, providing a complete audit trail of the user onboarding process.
3. Role-Based Access Control
The Role-Based Access Control (RBAC) subsystem is the cornerstone of the system's security architecture, governing which modules, features, and data each user can access based on their assigned role. The RBAC model operates on a hierarchical principle where roles define collections of permissions, users are assigned one or more roles, and the system enforces these role-based restrictions at every point of interaction, from sidebar navigation rendering to API endpoint authorization. This approach provides a scalable and maintainable access control framework that can accommodate complex organizational structures without requiring per-user permission configurations. The system distinguishes fundamentally between administrative and employee-level access, with the ability to dynamically toggle between these modes within the same authenticated session.
3.1 Admin vs Employee Mode Toggle
The system supports a dynamic mode toggle mechanism that allows users with administrative privileges to switch between an Admin view and an Employee view of the application without requiring a separate login. This toggle is implemented as an AJAX call to the changeAdminToEmployee endpoint, which flips a session-level flag indicating which permission set should be applied to subsequent requests. When operating in Admin mode, the user sees the full range of administrative modules and tools available to their role, including user management, system configuration, and advanced reporting features. When switched to Employee mode, the interface is stripped down to reflect the permissions and modules available to a standard employee, providing administrators with the ability to preview and test the employee experience firsthand.
The mode toggle is a session-scoped operation, meaning it does not permanently change the user's role assignment or database records; it only affects the current session's permission context. This design allows administrators to freely switch between modes during their workflow without any lasting impact on their account configuration. The current mode is reflected in the sidebar through a visible role label (e.g., "ADMIN") that keeps the user aware of which permission context is active. This feature is particularly valuable during training, troubleshooting, and user support scenarios where administrators need to replicate the exact experience that an employee would encounter when interacting with the system. The session-level implementation also ensures that switching modes does not interfere with other active sessions the user may have on different devices.
3.2 Role Label in Sidebar
The sidebar navigation component prominently displays the current user's active role label, providing constant visual confirmation of the permission context in effect. When the user is operating in administrative mode, the label displays "ADMIN" in a visually distinct style (typically highlighted with the application's accent color or bold formatting) to clearly differentiate it from the standard employee context. This label serves as both an informational indicator and a safety mechanism, preventing users from inadvertently performing administrative actions while believing they are in employee mode. The role label is dynamically updated whenever the mode toggle is invoked, ensuring that the UI always accurately reflects the current session state without requiring a page reload.
The sidebar itself is dynamically generated based on the active role and its associated module permissions. When the user toggles from Admin to Employee mode, the sidebar immediately re-renders to show only the modules and menu items that an employee role is permitted to access. Modules such as User Management, System Configuration, and Role Administration are hidden in Employee mode, while modules like Purchase Orders, Requisitions, and Vendor Management remain visible. This dynamic sidebar rendering provides a clear, tangible demonstration of the RBAC system in action, as the user can observe the navigation structure changing in real time when they switch modes. The sidebar also displays the user's display name and profile image at the top, reinforcing the personalized nature of the authenticated session.
3.3 Module-Level Access Control
Module-level access control is the primary enforcement mechanism of the RBAC system, determining which application modules appear in the user's navigation and which API endpoints they are authorized to invoke. Each module in the system is assigned a set of required permissions, and each role is configured with a corresponding set of granted permissions. When a user authenticates, the system loads their role's permission set and uses it to filter the available sidebar menus, hide unauthorized UI elements, and reject requests to protected endpoints. This three-layer enforcement (UI filtering, client-side route guarding, and server-side API authorization) ensures that access restrictions cannot be circumvented through direct URL manipulation or API call spoofing.
The permission model supports both positive permissions (explicitly granting access to a module) and negative permissions (explicitly denying access), with denial taking precedence over grant in cases of conflict. This allows administrators to create nuanced role configurations where a broadly-permissioned role can have specific modules excluded without having to enumerate every other module individually. Module-level permissions can be further refined with action-level granularity within certain modules, for example allowing a user to view purchase orders but not create or approve them. The configuration of module permissions is managed through the Role Administration interface, which provides a matrix-style UI where administrators can toggle individual module access for each role. Changes to role permissions take effect immediately for all users assigned to the modified role, requiring no session restart or user action.
3.4 Notification-Based Action Routing
The RBAC system integrates with the notification framework to implement a workflow-driven access pattern where users are notified of pending actions that require their attention based on their role. Rather than requiring users to actively search for tasks within each module, the system proactively delivers notifications when an action requiring the user's role-based authority enters their queue. For example, when a purchase requisition is submitted and requires managerial approval, the system generates a notification directed to all users holding the Manager role with procurement approval permissions. This notification includes a direct link to the approval action, allowing the manager to navigate directly to the relevant workflow step with a single click.
This notification-based routing pattern transforms the RBAC system from a passive access gate into an active workflow orchestrator. Users are not only restricted from accessing modules outside their role but are also guided toward the modules and actions that are most relevant to their responsibilities. The notification system respects role hierarchies and delegation rules, ensuring that notifications are directed to the appropriate role level even in complex organizational structures with multiple approval tiers. If a notification recipient is unavailable, the system can be configured to escalate the notification to a designated backup or to a higher-level role, preventing workflow bottlenecks. This integration between access control and notification routing creates a cohesive operational environment where users are always aware of their pending responsibilities and can act on them efficiently.
4. User Profile
The User Profile module, identified by the command COM_VIEW_PROFILE_APPLICATION_USERS, provides a self-service interface that allows individual users to view and manage their own account information without requiring administrative intervention. This module is accessible from the top header bar of the application, typically through a user avatar or dropdown menu that appears in the upper-right corner of every page. The profile interface presents the user's current information in a read-optimized layout and provides edit controls for fields that the user is permitted to modify. The self-service nature of this module reduces the administrative burden on IT support staff while empowering users to maintain accurate and up-to-date personal information within the system.
The profile page displays the user's personal details including their first name, last name, display name, email address, and mobile number, along with their organizational attributes such as assigned location, country, and current role. Users can update their display name, profile image, and contact information directly through the profile interface. However, certain sensitive fields such as the user's email address (which serves as the login identifier) and role assignment are either restricted to read-only access or require additional verification before modification, preventing unauthorized changes to security-critical attributes. The profile module also provides access to security settings such as password change functionality and session management, allowing users to review and terminate their active sessions across different devices.
The profile management interface is designed with a clean, form-based layout that groups related fields into logical sections for easy navigation. Profile image upload supports common image formats with automatic resizing and cropping to ensure consistency across the application's UI. When a user updates their profile, the changes are immediately reflected in the header bar's display name and avatar, as well as in any notifications or workflow entries that reference the user's identity. The profile module maintains an audit log of profile changes, recording the timestamp, field modified, previous value, and new value for each update, providing a complete change history that supports both compliance requirements and the ability to revert inadvertent modifications.
5. Notification System
The Notification System is a pervasive cross-cutting component that keeps users informed about events, actions, and system occurrences that are relevant to their role and responsibilities within the Procurement Management System. The system is designed around three distinct notification categories that serve different informational purposes, and it is deeply integrated into the application's workflow engine, access control subsystem, and module-level event handlers. Notifications are delivered through a combination of in-app visual indicators, a popup panel, and (where configured) external channels such as email, ensuring that users remain aware of important events regardless of their current focus within the application.
5.1 Notification Types
The system classifies notifications into three primary categories, each serving a distinct purpose within the application's operational workflow. Action notifications are generated when a workflow step requires the user's intervention, such as a document awaiting approval, a task assigned for completion, or a procurement request pending review. These notifications are time-sensitive and typically include a direct action link that navigates the user to the relevant workflow screen. Information notifications communicate general updates that do not require immediate user action, such as system announcements, policy changes, or status updates on documents the user has previously interacted with. Log notifications record and present system events and audit trail entries, providing users with visibility into activities that have occurred within their scope of access, such as login events, data modifications by other users, and system configuration changes.

5.2 Notification Bell Icon and Badge Count
The notification bell icon is a persistent UI element displayed in the application's top header bar, providing users with an at-a-glance indicator of unread notifications. The icon features a numerical badge that displays the count of unread notifications across all three notification types, creating a visual urgency signal that encourages timely attention to pending items. The badge count is dynamically updated through periodic AJAX polling, ensuring that the displayed number remains current even when new notifications arrive while the user is actively working in the application. When the unread count reaches zero, the badge is hidden or reduced to a neutral state, providing clear visual feedback that all notifications have been reviewed.
Clicking the notification bell icon triggers the display of the notification popup panel, which presents the user's recent notifications in a scrollable, categorized format. The popup is rendered through the view template views/custom_list_notification_popup.php, which generates a compact, overlay-style panel that appears adjacent to the bell icon. The panel displays notifications in reverse chronological order, with the most recent items at the top, and includes visual indicators that distinguish between the three notification types through color coding or icon differentiation. Each notification entry in the popup includes a brief summary text, a timestamp, and (for Action-type notifications) a link to the relevant workflow step. The popup supports both individual notification dismissal and bulk "mark all as read" operations through dedicated AJAX endpoints.
5.3 AJAX Endpoints for Notification Management
The notification system exposes two dedicated AJAX endpoints for managing notification state from the client side. The first endpoint, ajax.php?page=closenotificationinfo, accepts a notification identifier parameter and marks the specified notification as read or dismissed. This endpoint is called when a user clicks the dismiss button on an individual notification within the popup panel, and it returns a success status along with the updated unread count, allowing the client to refresh the bell icon badge without a full page reload. The second endpoint, ajax.php?page=closeallnotifications, operates without parameters and marks all unread notifications for the current user as read in a single operation, corresponding to the "Mark All as Read" action available in the notification popup header.
Both endpoints follow the system's standard AJAX response pattern, returning JSON-encoded payloads that include a status code, a human-readable message, and any updated data required by the client (such as the revised unread count). These endpoints enforce server-side validation to ensure that users can only dismiss or close notifications that belong to them, preventing cross-user notification manipulation. The endpoints also trigger server-side event hooks that can be used to update notification analytics, feed workflow state machines, or generate audit log entries when notifications are dismissed. This endpoint design supports the responsive, real-time feel of the notification system while maintaining strict server-side authorization controls over notification state transitions.
6. Internal Messaging
The Internal Messaging module, identified by the command COM_LIST_INBOX, provides a built-in communication channel that enables users to exchange messages with one another without leaving the Procurement Management System. This module is particularly valuable in procurement workflows where communication between requesters, approvers, and procurement officers needs to be documented and associated with specific transactions or documents. The messaging system is accessible from the top header bar through a "My Messages" link, which navigates the user to their personal inbox where they can view received messages, compose new messages, and manage their message folders. The inbox follows familiar email-client conventions with a message list view and a message detail view, minimizing the learning curve for new users.
Messages can be addressed to individual users by selecting recipients from the system's user directory, and the messaging module supports both one-to-one and one-to-many communication patterns. Each message includes standard fields for sender, recipient(s), subject, body content, timestamp, and read status. The system maintains message threads to preserve conversational context, allowing users to follow the flow of discussion around a particular topic or procurement document. When a new message is received, the messaging module generates a notification (through the notification system described in Section 5) to alert the recipient, creating a seamless connection between the two subsystems. The messaging interface is fully integrated with the application's authentication and RBAC systems, ensuring that messages can only be sent to active users within the same tenant and that message access is governed by the recipient's role permissions.
The internal messaging system also supports file attachments, allowing users to share documents, images, and other files alongside their message content. Attachments are stored within the system's file management infrastructure and are subject to the same access controls as the messages they accompany. The inbox provides standard message management operations including reply, forward, delete, and archive, and users can organize their messages through a folder structure or search and filter functionality. The integration of internal messaging within the procurement platform eliminates the need for external communication tools for routine procurement discussions, keeping all relevant communication within the system's audit trail and ensuring that message history is accessible alongside the related procurement documents and workflows.
7. Configuration Module
The Configuration Module, accessed through the command COM_INSERT_CONFIG, provides a centralized interface for managing the organizational and system-wide settings that govern the Procurement Management System's behavior. This module is restricted to administrative users and encompasses a comprehensive set of configuration categories covering company identity, regional preferences, financial defaults, accounting parameters, and document formatting. All configuration values are scoped to the current tenant, ensuring that each organization can customize the system to match its operational requirements without affecting other tenants. The module employs an effective dating mechanism using from_date and to_date fields, allowing administrators to schedule configuration changes in advance and maintain a historical record of how settings have evolved over time.
7.1 Company Settings
The Company Settings section captures the core organizational identity and legal registration information that appears on system-generated documents, invoices, and official communications. The company name field defines the primary display name used throughout the application, while the display_logo file upload allows administrators to brand the application with their organization's logo. Legal and tax identification fields include liscense_number, tax_number, gst_number (Goods and Services Tax identification), cin_number (Corporate Identification Number), and pan_number (Permanent Account Number), each serving specific regulatory compliance requirements in different jurisdictions. Contact information fields such as phone_number and fax_number provide standard communication channels that are printed on documents and available in the organization's public-facing profile within the system.

7.2 Address Configuration
The Address Configuration section provides two textarea fields for defining the organization's physical locations. The billing_address field captures the official address used on invoices, purchase orders, and other financial documents, which may differ from the organization's primary contact location. The contact_address field stores the general correspondence address where non-financial communications and vendor-facing documents should be directed. The use of separate billing and contact addresses accommodates organizations that maintain different addresses for financial versus general correspondence, a common requirement for businesses with registered offices in one location and operational headquarters in another. Both address fields support multi-line text input, allowing for structured address entries that include street address, city, state/province, postal code, and country information.
7.3 Regional Settings
The Regional Settings section controls how the system formats dates, numbers, and percentages to match the organization's local conventions and regulatory requirements. The time_zone field defaults to Asia/Kolkata but can be configured to any standard timezone, ensuring that timestamps throughout the system (document dates, audit logs, notification times) are rendered in the organization's local time. The date_format field is set to DD-MM-YYYY by default, defining the display order for calendar dates, while the date_separator field specifies the character used between date components (defaulting to a hyphen). The percentage_position field controls whether percentage values are displayed with the symbol preceding or following the numeric value (e.g., "10%" versus "%10"). The number_format field, defaulting to "1.2", defines the decimal precision and grouping conventions for numeric values displayed throughout the application, ensuring consistency in financial figures, quantities, and measurements.

7.4 Financial Configuration
The Financial Configuration section establishes the monetary and accounting defaults that govern the system's financial operations. The default_currency_id field links to the system's currency reference table, setting the base currency for all financial transactions, invoice amounts, and budget displays. The default_language_id field determines the language used in system-generated financial documents and communications. The kpi_mode toggle (1 for enabled, 0 for disabled) controls whether Key Performance Indicator dashboards and metrics are activated for the organization. The default_payment_mode field sets the preferred payment method for purchase orders and vendor payments, while default_cash_acct and default_tax_account define the default ledger accounts for cash transactions and tax postings respectively. The subscription_info field stores the organization's current subscription tier and entitlement details, while application_module defines which functional modules are enabled for the tenant. The copy_right field allows customization of the copyright notice displayed in the application footer and on generated documents.
7.5 Accounts Configuration
The Accounts Configuration section defines the default ledger account mappings used by the system's automated journal entry and financial posting routines. These account settings ensure that financial transactions are consistently posted to the correct general ledger accounts without requiring manual account selection for each transaction. The jv_suspense_acc field specifies the suspense account used for journal voucher entries that require manual reconciliation. The default_bank_account_id field identifies the primary bank account used for payment processing and bank reconciliation. The tds_clearing_account and tds_payables fields define the ledger accounts for Tax Deducted at Source (TDS) clearing and liability tracking, while the tcs_clearing_account and tcs_payables fields serve the equivalent purpose for Tax Collected at Source (TCS). These pre-configured account mappings streamline the accounts payable and receivable workflows by eliminating repetitive account selection steps and ensuring compliance with tax accounting requirements.

7.6 Document Configuration
The Document Configuration section controls the formatting and numbering conventions for system-generated documents such as invoices, purchase orders, and assessment reports. The invoice_perfix and invoice_postfix fields (note the spelling as found in the system) define optional text strings that are prepended and appended to auto-generated invoice numbers, allowing organizations to create meaningful document identifiers that align with their existing numbering schemes. For example, an organization might set the prefix to "INV-" and the postfix to "-2026" to produce invoice numbers like "INV-000123-2026". The default_country_id field sets the default country context for new documents, pre-populating country-dependent fields such as tax calculations and delivery terms. The assessment_year field defines the fiscal year context for tax-related documents and computations. The location field specifies the default operating location that appears on generated documents, typically corresponding to the organization's primary business address.
7.7 Effective Dating (from_date / to_date)
The Configuration Module employs an effective dating mechanism through from_date and to_date fields that allows administrators to create time-bound configuration records. Each configuration entry can specify the date range during which it should be considered active, enabling organizations to plan and schedule configuration changes in advance. For example, an organization anticipating a change in its default tax rate at the start of a new fiscal year can create a new configuration record with a from_date matching the fiscal year start, and the system will automatically transition to the new settings on the specified date without requiring manual intervention. This approach eliminates the risk of configuration drift and ensures that financial and operational settings are always aligned with the correct time period.
The effective dating system also provides a complete audit trail of configuration changes over time, as each historical configuration record is preserved in the database rather than being overwritten. Administrators can review past configurations to understand how settings were structured during any given period, which is invaluable for financial audits, regulatory compliance reviews, and troubleshooting issues that may have been caused by a configuration change. When determining which configuration record to apply for a given request, the system evaluates the current date against the from_date and to_date ranges of all configuration records for the tenant and selects the record whose effective period encompasses the current date. If multiple records overlap or if no active record is found for the current date, the system falls back to the most recent expired record or raises a configuration error, ensuring that the application never operates with undefined or ambiguous settings.
