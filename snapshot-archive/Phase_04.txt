================================================================================
PHASE 4: INVENTORY & ITEM MANAGEMENT - CODE & DATABASE LEVEL ANALYSIS
================================================================================

This document provides deep code-level and database schema analysis
of the Inventory & Item Management modules, scraped from the live application.

---
1. APPLICATION ARCHITECTURE (CODE LEVEL)
---

1.1 Technology Stack
  - Backend: PHP (server-rendered, no REST framework)
  - Frontend: jQuery + Bootstrap 4 + DataTables + Select2
  - Database: MySQL (inferred from PHP/LAMP stack)
  - Session: PHP sessions (PHPSESSID cookie)
  - Routing: Single entry point (index.php) with option-based routing

1.2 Module Overview
  The Inventory module comprises 6 sub-modules:
  - item_categories    (COM_INSERT_ITEM_CATEGORIES)
  - item_types         (COM_INSERT_ITEM_TYPES)
  - unit_of_measurements (COM_INSERT_UNIT_OF_MEASUREMENTS)
  - items              (COM_INSERT_ITEMS)
  - hsn_and_sac_codes  (COM_INSERT_HSN_AND_SAC_CODES)
  - currencies         (COM_INSERT_CURRENCIES)

  All modules follow the generic form generator pattern via
  views/new_from.php?option=COM_INSERT_XXX. The items module is
  flagged as has_line_items=True, indicating a line-item sub-form
  for item-level details (pricing tiers, stock entries, etc.).

1.3 Routing Convention
  COM_LIST_ITEM_CATEGORIES        -> List/view page
  COM_INSERT_ITEM_CATEGORIES      -> Insert form
  COM_UPDATE_ITEM_CATEGORIES      -> Update form
  COM_LIST_ITEM_TYPES             -> List/view page
  COM_INSERT_ITEM_TYPES           -> Insert form
  COM_LIST_UNIT_OF_MEASUREMENTS   -> List/view page
  COM_INSERT_UNIT_OF_MEASUREMENTS -> Insert form
  COM_LIST_ITEMS                  -> List/view page
  COM_INSERT_ITEMS                -> Insert form
  COM_LIST_HSN_AND_SAC_CODES      -> List/view page
  COM_INSERT_HSN_AND_SAC_CODES    -> Insert form
  COM_LIST_CURRENCIES             -> List/view page
  COM_INSERT_CURRENCIES           -> Insert form

2.1 Table: item_categories
  Module: Item Categories
  Insert Option: COM_INSERT_ITEM_CATEGORIES

  CREATE TABLE item_categories (
    id INT AUTO_INCREMENT PRIMARY KEY,
    category_description VARCHAR(500),
    default_costing_type ENUM('S','W') DEFAULT 'S',
      -- S = Standard Costing, W = Weighted Average
    first_removal_strategy ENUM('FIFO','LIFO','LEFO','CL') DEFAULT 'FIFO',
      -- CL = Close (lot/serial)
    price_variance ENUM('Y','N') DEFAULT 'N',
    price_variance_amount_min DECIMAL(15,2) DEFAULT 0,
    price_variance_amount_max DECIMAL(15,2) DEFAULT 0,
    price_variance_type ENUM('P','A') DEFAULT 'P',
      -- P = Percentage, A = Amount
    qty_variance ENUM('Y','N') DEFAULT 'N',
    qty_variance_amount_min DECIMAL(15,2) DEFAULT 0,
    qty_variance_amount_max DECIMAL(15,2) DEFAULT 0,
    qty_variance_type VARCHAR(20) DEFAULT 'Percentage',
      -- 'Percentage' or 'Amount' (note: inconsistent enum vs string)
    industry_id INT DEFAULT 0,
      -- FK to industries/sectors lookup
    inventory_asset_account INT DEFAULT 0,
      -- FK to chart_of_accounts for inventory valuation
    status TINYINT DEFAULT 0,
      -- 0=Active, 1=Inactive, 2=Draft
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
  );

  Note: No effective dating (from_date/to_date) on this table.
  No mandatory_str was scraped (may be set dynamically).

4. BUSINESS RULES
---

4.1 Costing Types
  Two levels of costing configuration exist:
  1. Category-level default_costing_type: ENUM('S','W')
     S=Standard, W=Weighted Average (simplified at category level)
  2. Item-level default_costing_type: ENUM('F','L','S','W')
     F=FIFO, L=LIFO, S=Standard, W=Weighted Average
  Item-level setting overrides category default when specified.

4.2 Removal Strategies
  Configured at item category level via first_removal_strategy:
  - FIFO  (First In First Out)
  - LIFO  (Last In First Out)
  - LEFO  (Last Expiry First Out)
  - CL    (Close / Lot-specific)
  This determines which stock lots are consumed first in
  dispatch/delivery transactions.

4.3 Price and Quantity Variance Tolerance
  At category level, two variance controls exist:
  - price_variance (Y/N): Enable price tolerance checking
    price_variance_type: P=Percentage, A=Amount
    price_variance_amount_min/max: tolerance bounds
  - qty_variance (Y/N): Enable quantity tolerance checking
    qty_variance_type: 'Percentage' or 'Amount'
    qty_variance_amount_min/max: tolerance bounds
  These control whether purchase orders/invoices can deviate
  from quotations without approval.

4.4 Item Tracking
  tracking_type determines inventory traceability:
  - 0: No tracking (quantity-only)
  - 1: Batch tracking (batch/lot numbers)
  - 2: Serial number tracking (individual serial numbers)
  quantity_check (1=enabled, 2=disabled) controls whether
  the system validates stock availability at transaction time.

4.5 Stock Control Flags
  - negative_stock: If Y, allows stock to go below zero
  - allow_back_order: If Y, enables back-ordering when stock
    is insufficient
  - quality_check: If Y, requires quality inspection before
    stock is made available
  - sold_individually: If Y, item is sold as single unit
  - sold_in_groups: If Y, item is sold in predefined groups

4.6 GST Handling via HSN/SAC Codes
  HSN (Harmonized System Nomenclature) codes for goods
  SAC (Services Accounting Code) for services
  Each code carries a default GST rate (gst field).
  During transaction line-item entry, the HSN code of the item
  determines the applicable tax rate. The system calculates:
  - CGST = (taxable_value * gst_rate / 2) for intra-state
  - SGST = (taxable_value * gst_rate / 2) for intra-state
  - IGST = (taxable_value * gst_rate) for inter-state
  This is inferred from the originator_state_id and
  supplier_state_id hidden fields on transaction forms.

4.7 Opening Quantity
  Items support an opening_quantity field for initial stock
  setup during implementation. Default is 0.

4.8 Effective Dating
  item_types, unit_of_measurements, and hsn_and_sac_codes
  support effective dating (from_date/to_date). item_categories
  and currencies do not. from_date is always mandatory.

6. SOURCE CODE PATTERNS
---

6.1 Stock Balance Check (custom.js lines 1138-1164)
  The getStockBalanceAvailability() function is a synchronous
  AJAX call that validates inventory before status transitions:

  function getStockBalanceAvailability(transaction_table, transaction_id) {
    var session_config_json = JSON.parse($("#session_config_json").val());
    let retres = 0;
    $.ajax({
      url: 'ajax.php',
      type: "POST",
      async: false,   // BLOCKING - waits for response
      data: 'page=getstockbalanceavailability&transaction_table='
            + transaction_table + '&transaction_id=' + transaction_id,
      success: function(response) {
        var res = JSON.parse(response);
        if (res.errorthrow.errorcount != 0) {
          var errormsg = "Item ";
          $.each(res.errorthrow.details, function(index, itemdet) {
            errormsg += itemdet.item_name + " has only "
              + itemdet.closing_qty + " qty available - you applied "
              + itemdet.sum_item_quantity + " qty. , ";
          });
          errormsg += "Please check stock before applying.";
          swal(session_config_json.name, errormsg, "error");
          retres = 1;  // BLOCK the status change
        }
      }
    });
    return retres;
  }

  Currently gated for delivery_orders and sales_invoices only.
  The pattern in submitDynamiPopUpForm() shows:
    if (table == 'delivery_orders' || table == 'sales_invoices') {
      result = getStockBalanceAvailability(table, id);
    }
    if (result == 0) { proceed with status change; }

6.2 HSN-GST Calculation (Inferred Backend Pattern)
  While no client-side GST calculation JS was scraped, the
  backend calculates tax based on:
  1. Item's hsn_sac_code_id -> hsn_and_sac_codes.gst
  2. Transaction's originator_state_id vs supplier_state_id
  3. If states match (intra-state): CGST + SGST = gst/2 each
  4. If states differ (inter-state): IGST = full gst
  The hidden fields originator_state_id and supplier_state_id
  on transaction forms carry these values. Place of supply
  determines the GST type.

6.3 Checkbox to Hidden Field Pattern
  The application uses dual hidden+checkbox fields for booleans:
  Hidden field: <input type="hidden" name="sold_individually" value="">
  Visible field: <input type="checkbox" name="sold_individually" value="0">
  When unchecked, the hidden field carries empty string.
  When checked, the checkbox value (0) is submitted.
  This is a known pattern where value="0" maps to Y/true.

6.4 Category-Level Inheritance
  Items inherit defaults from their item_category:
  - default_costing_type (if item-level not set)
  - first_removal_strategy
  - price_variance tolerance
  - qty_variance tolerance
  The item form has its own costing_type dropdown with 4 options
  (F/L/S/W) which overrides the category's 2-option (S/W) default.

6.5 Generic Form Generator
  All inventory modules use views/new_from.php which reads
  field metadata from the system's field_metadata table and
  renders the appropriate form controls. The hidden fields
  (in_date_pic, mandatory_str, duplicate_table_name, etc.)
  drive framework behavior.
