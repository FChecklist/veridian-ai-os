## OBJECTIVE
Fix two real, recurring root causes in the shared /opt/veridian/scripts/supervisor-entrypoint.sh + scripts/auto_phase_continuation.py pipeline that have forced manual intervention after every single phase of the VERIDIAN_ARCHITECTURE_V2 initiative merged so far (phase_1, phase_2), and will keep forcing it on every future phase across every initiative that uses this same auto-continuation mechanism unless fixed at the source. Confirmed real instances this session: phase_1 (compliance-tracker PR #559) and phase_2 (compliance-tracker PR #560) both merged successfully but needed a human to manually backfill their own phase-plan status afterward; phase_2 additionally needed a human to manually re-run a failed CI job by hand.

## KNOWN_CONTEXT
- Root cause 1 -- workers do not self-report phase completion: is_phase_done() in scripts/auto_phase_continuation.py requires a phase's own YAML entry to already have a self-reporting status field (checked by _self_reports_done()) before it will even attempt the real merged-PR cross-reference -- if that self-report is missing, the phase is treated as not-done regardless of real merge state, permanently blocking auto-dispatch of whatever depends on it. build_prompt() already tells the dispatched worker to update its own phase-plan entry (see its EXPECTED_OUTPUT text), but real evidence from two consecutive real phases shows workers do not reliably do this -- relying on worker discipline has now failed twice in a row. The real, systemic fix is to make this SOFTWARE's responsibility, not the worker's: after a tier1 PR auto-merges (or a tier2 PR's approval is confirmed), the same script/step that confirms the merge should also write the self-report fields (status/completed_by_task/evidence) into the correct phase-plan file automatically -- no reliance on the worker having done it.
- Root cause 2 -- CI-timing race on the required audit-check job: compliance-tracker's audit-check GitHub Actions job runs on PR open/synchronize and fails immediately with "No structured audit verdict found" if it runs before supervisor-entrypoint.sh's real Claude-driven review has finished and posted its AUDIT: PASS/FAIL comment -- since that review takes real time (a genuine LLM call), this race is expected to recur on every PR, not a one-off fluke. Real evidence: PR #560's audit-check failed at 23:39:15, before the AUDIT: PASS comment existed; manually re-running the same job after the comment existed made it pass. The real fix is either (a) have compliance-tracker's audit-check workflow also trigger on `issue_comment` events (re-running itself when a new PR comment is posted), or (b) have supervisor-entrypoint.sh itself trigger a re-run of the audit-check job (`gh run rerun <run-id> --failed` or equivalent, `gh workflow run`/`gh api .../rerun`) immediately after it posts its own AUDIT comment. Determine which is the smaller, more reliable real fix and implement it -- read the actual audit-check workflow file in compliance-tracker's .github/workflows/ first to understand its real trigger configuration before choosing.
- Both fixes are shared infrastructure (not specific to VERIDIAN_ARCHITECTURE_V2) -- fixing them here benefits every current and future initiative using this same auto-continuation + supervisor pipeline (20-Engines, Auditor Engine, Testing Engine, Terminology, Wiring Engine already completed without hitting this as visibly, likely because their own phase-1 dispatches happened to have workers that DID self-report, or their timing didn't race -- do not assume this is new, it is a latent bug that just became visible now).
