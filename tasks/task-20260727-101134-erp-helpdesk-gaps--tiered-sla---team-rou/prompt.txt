## SCOPE
1. **Tiered, policy-based SLA + team routing**: confirmed absent (grepped `slaPolic`/`sla_polic`/`escalationRule`/`businessHours` across schema.ts, zero matches). Build: an SLA-policy table (by team/priority/category, with business-hours-aware countdown), an escalation-rule table (chain of assignees/teams on breach), and a team/queue concept for `tickets.assigneeId` (currently a single free-form field with no team/queue routing). Wire ticket creation to resolve its SLA deadline from the matching policy instead of the current manually-supplied `input.slaHours`, preserving backward compatibility for tickets that still pass an explicit override.
2. **Email-to-ticket ingestion**: not confirmed to exist either way -- verify first (a parallel pattern exists for email generally, `emailIntelligenceItems` schema.ts:9954, which promotes to `tasks`, but nothing was found promoting an inbound email specifically into a `tickets` row -- confirm this with a real grep/read before building, then build a real inbound-email-to-ticket path if genuinely absent, reusing whatever email-ingestion infrastructure `emailIntelligenceItems` already has rather than building a second one).
3. **Public self-service portal**: verify first whether `knowledgeBasePages` has any internal/external-published flag, and whether a customer can browse KB or self-raise a ticket without a staff-issued guest link today (not verified at the UI layer per the Phase 0 investigation). If genuinely absent, build a minimal real self-service surface: a public KB browse view (respecting the internal/external flag you add if none exists) and a "raise a ticket" form usable without a pre-issued guest link (still real -- creates a genuine guest-scoped conversation/ticket via the existing conversationGuestAccess mechanism, not a new parallel one).
