## OBJECTIVE
Close two real, confirmed gaps in VERIDIAN's task-lifecycle automation: there is currently no proactive status-monitoring software (an Owner/AI asking "status" today means manually running gh/task.yaml checks by hand, not reading real software output), and no automatic remediation trigger when a real task/PR gets rejected or blocked (a human/AI has to happen to notice and manually dispatch a fix). Build both as real, cron-driven software using tools that already exist -- do not invent a new framework.

## KNOWN_CONTEXT
- Confirmed via direct grep of the real live crontab and /opt/veridian/scripts/ (2026-07-26): task-gateway.py, OWNER_ENGINE, worker-entrypoint.sh, supervisor-entrypoint.sh (with backfill_phase_self_report.py + the audit-check-rerun block, both confirmed live), auto_phase_continuation.py, and supervisor-sweep.sh are all real and already cron-driven. This task does NOT touch or duplicate any of those -- it adds a monitoring/alerting layer that reads their real output, and a remediation-dispatch layer that reacts to it.
- Real data sources already available for a monitor to read, no new instrumentation needed: /opt/veridian/ai-os/tasks/*/task.yaml (real status + checkpoint history per task), `gh pr list --repo <repo> --state open --json number,state,statusCheckRollup,mergeStateStatus` per tracked repo (claude-control, compliance-tracker, projexa), and each open PR's real audit comments via `gh api repos/<owner>/<repo>/issues/<pr>/comments`.
- "Proactive" means the software itself decides something needs attention and writes that down somewhere real and checkable on a regular cadence -- it does not require paging/notifying a human in real time (no such channel exists here); it means a single, real, structured, current status artifact this assistant can read INSTEAD of manually re-deriving status from scratch every time it's asked, and a real log of what the remediation layer did automatically.
- Remediation scope for THIS task: when the monitor finds a real AUDIT: FAIL comment on an open PR with no corrective commit pushed since that comment's timestamp, or a task blocked by a real (non-transient) merge conflict, it should draft a real, watertight corrective task prompt (same OBJECTIVE/SCOPE/KNOWN_CONTEXT/SUCCESS_CRITERIA/EXPECTED_OUTPUT/CONSTRAINTS/COMPLEXITY_TIER format tight_task_validation.py already requires) referencing the real findings, and either (a) auto-dispatch it directly via task-gateway.py if the finding is a real, mechanical, low-risk class (e.g. a confirmed CI-timing race, a confirmed transient network/5xx merge failure) -- reusing the same real fix mechanisms already built (audit-check rerun, retry-with-backoff for transient merge failures) -- or (b) for anything requiring real judgment (a genuine security/correctness finding like the cross-tenant bug found today), write the drafted corrective prompt to a real, clearly-named pending file and flag it in the status artifact as "drafted, needs assistant review before dispatch" rather than auto-dispatching unreviewed code-level fixes. Do not have this layer merge anything or make judgment calls about real security/correctness findings on its own.

## SCOPE
1. Write scripts/veridian_status_monitor.py: scans all real tracked task.yaml files + all real open PRs across claude-control/compliance-tracker/projexa, and writes a single real, structured status artifact (ai-os/LIVE_STATUS_2026-07-26.yaml) containing: tasks currently in_progress (with real elapsed time), tasks blocked (with the real reason, read from the real checkpoint note/review.json), PRs open with a real AUDIT: FAIL and no corrective commit since, PRs stuck on a real non-transient merge conflict, and phases ready to auto-advance per auto_phase_continuation.py's own real --dry-run output. Overwrite the artifact each real run (it is a live snapshot, not an append log).
2. Wire it into a real cron entry (same run-logged.sh + Owner-approval-citation pattern as every other crontab addition this session) at a real, reasonable cadence (every 10 minutes is reasonable given the Owner's own stated 10-minute communication cadence).
3. Write scripts/veridian_remediation_dispatcher.py implementing the real remediation scope from KNOWN_CONTEXT -- reads the same real blocked/rejected findings the status monitor surfaces, classifies each as auto-fixable-mechanical vs needs-judgment per KNOWN_CONTEXT's real examples, auto-dispatches the mechanical ones for real, and writes judgment-needed ones as real drafted-but-not-dispatched prompt files plus a clear flag in the status artifact.
4. Wire the dispatcher into the same cron cadence as the monitor (or immediately after it in the same cron entry).
5. Real-test both: run the monitor once for real against the real current system state and show its real output; if any real blocked/rejected item exists at test time, show the dispatcher's real classification and action for it (or state honestly if none existed at test time, and construct one safe real test case, e.g. a deliberately-rejected throwaway task, to prove the mechanical-auto-fix path works, then clean up the throwaway).
6. Update ai-os/MASTER_INDEX.yaml (registries.status_monitor_and_remediation) and register via superboss-register.py.

## SUCCESS_CRITERIA
- `python3 scripts/veridian_status_monitor.py` exits 0 and `ai-os/LIVE_STATUS_2026-07-26.yaml` parses as real, valid YAML with real, current data (not stale/fabricated) after running it.
- `crontab -l | grep -c veridian_status_monitor` returns 1 or more (real cron entry exists).
- A real test proves the remediation dispatcher correctly classifies at least one real or deliberately-constructed case into each of its two paths (auto-dispatch mechanical, draft-for-review judgment) -- paste the real test evidence for both paths.

## EXPECTED_OUTPUT
Real committed and pushed code (PR on claude-control) for both scripts, the real cron wiring (with the Owner-approval-citation entry in ai-os/OWNER_DECISIONS_NEEDED_2026-07-23.yaml, same pattern as every prior crontab addition), the real first-run status artifact, real test evidence for both remediation paths, the MASTER_INDEX registration, and a final checkpoint stating plainly what is now proactively monitored versus what still requires this assistant's own judgment (and why, for each judgment-required case named).

## CONSTRAINTS
The remediation dispatcher must never merge a PR or resolve a real security/correctness finding on its own -- only draft a corrective task for assistant review, or auto-dispatch for the narrow, explicitly-named mechanical classes (CI-timing race rerun, transient merge-failure retry) that already have a proven-safe existing fix pattern.
