1. **Budget-undercount bug (the primary blocker)**: `aggregateDesignerTimesheetCosts()`'s `designerStatusByUser` is built only from time entries, not from the full user roster. A designer with a real `pms_budget_line_items` row but zero time entries anywhere in the org (e.g. a newly-budgeted designer who hasn't logged hours yet) is silently excluded from both the active and inactive buckets -- so `sum(byDesignerStatus.budget)` silently diverges from `overallBudget` in a plausible, real-world state, with no error surfaced. `designerTimesheetReport()` already fetches the full user roster elsewhere -- pass it in to fix this, do not re-fetch.
2. **Real N+1 performance bug**: `designerTimesheetReport()` calls the DB-querying `resolveBillableRate()` once per time entry inside a sequential for-loop over EVERY time entry in the entire org (not just the requested project), even though `pms-time-service.ts` already exposes a pure, pre-fetch-once variant (`resolvePmsBillableRatePure`) specifically to avoid this. Fix: fetch the org's billable rates ONCE upfront, then use `resolvePmsBillableRatePure` inside the loop, same pattern this same file already uses elsewhere.
3. **Scope-mixing bug**: the response mixes project-scoped fields (`byDesignerStatus`) with org-wide fields (`byDesigner`, `byProject`, `byCategory`) under a single `designerTimesheetReport(ctx, projectId)` call with no field-level indication of which scope each field represents -- likely to mislead a per-project report UI into showing data belonging to other projects. Fix: either scope ALL fields consistently to the requested project, or clearly separate/label project-scoped vs org-wide fields in the response shape (your call -- justify which, in the PR description).
