## OBJECTIVE
Build a real, technical (not documentary) guard that prevents an interactive Claude Code session from running mutating git/gh commands (git push to a protected branch, gh pr merge) directly against the server -- these actions must only happen through the real dispatch pipeline (task-gateway.py -> veridian-task.py -> systemd worker -> supervisor-entrypoint.sh). Real incident 2026-07-26: an interactive session ran `gh pr merge 78 --repo FChecklist/claude-control --merge --delete-branch` and `git push` (an empty retrigger commit to compliance-tracker) directly by hand after the automated pipeline's own merge/CI-trigger step failed, instead of diagnosing and fixing the pipeline's real bug. The standing rule ("AI agents work only through software, software follows process") currently has zero technical enforcement -- it only exists as a written rule an interactive session can simply not follow.

## KNOWN_CONTEXT
systemd sets INVOCATION_ID (and JOURNAL_STREAM) as real environment variables for every unit it launches -- confirmed present for veridian-worker@*.service units (spawned by scripts/veridian-task.py's systemd --user integration) and absent in a normal interactive SSH login shell. This is a real, checkable, un-spoofable-without-deliberate-effort signal to distinguish "this command is running inside a legitimate dispatched worker" from "a human or interactive AI session typed this directly." rajat's shell profile (~/.bashrc or ~/.profile on the server) is the right place for an interactive-session-scoped guard since it only affects interactive shells, not systemd units (systemd units don't source .bashrc).

## SCOPE
1. Add a bash function (in ~/.bashrc, sourced for interactive shells only) named `gh` that wraps the real `gh` binary: if the invoked subcommand is `pr merge` and `INVOCATION_ID` is unset in the environment, print a clear error ("BLOCKED: gh pr merge must run through the dispatch pipeline (task-gateway.py), not an interactive session -- see ai-os/OWNER_DIRECTIVES/PROTOCOL_OWNER_AI.yaml") and return a real non-zero exit code instead of executing. If INVOCATION_ID IS set (a real systemd-launched worker), pass through to the real gh binary unchanged. All other gh subcommands (view, checks, pr list, pr comment, pr diff, run rerun, and every other read-only or non-merge operation) must pass through unchanged in both cases; do not break normal verification/status-checking usage.
2. Add a similar guard for `git push` specifically when the target ref matches a protected-branch pattern (master, main) -- but do NOT block `git push` to a worker's own feature/task branch, since interactive verification/diagnostic work sometimes legitimately needs to inspect or rebase a branch. Read this repo's actual branch-protection config (`gh api repos/FChecklist/<repo>/branches/main/protection` / `.../master/protection`) to get the real protected branch names per repo rather than hardcoding a guess.
3. Apply this to the rajat user's shell profile on VERIDIAN-DEV (167.233.220.35) itself -- this is a server environment change, not a repo code change, so the real deliverable is the profile file's new content plus a committed copy of it (for auditability) at a real path in claude-control, e.g. ai-os/OWNER_DIRECTIVES/interactive-session-guard.bashrc-snippet, with a comment explaining what it does and referencing this real incident.
4. Write a real test: as a plain interactive shell (no INVOCATION_ID set), confirm `gh pr merge --help`-style dry attempt is blocked with the expected error and non-zero exit; as a simulated systemd-invocation (INVOCATION_ID set manually in the test's own environment), confirm it passes through.

## SUCCESS_CRITERIA
- `env -u INVOCATION_ID bash -lc 'gh pr merge 1 --repo some/repo --merge' ` (a real interactive-shell simulation) exits non-zero and prints the blocking message, without ever reaching the real gh binary or GitHub's API.
- `env INVOCATION_ID=test-unit-123 bash -lc 'gh --version'` (a real systemd-context simulation) still runs the real gh binary successfully (pass-through not broken for non-merge commands).
- `gh pr view 1 --repo FChecklist/claude-control` (a real read-only command) still works normally in an interactive shell -- verification/status commands must not be blocked, only pr merge and push-to-protected-branch.

## EXPECTED_OUTPUT
The real, working shell-profile change applied to rajat's account on VERIDIAN-DEV (167.233.220.35), plus a committed copy in claude-control at the path named above, plus the test. Document this in the one canonical protocol file (ai-os/OWNER_DIRECTIVES/PROTOCOL_OWNER_AI.yaml -- confirm via scripts/check_single_protocol_file.py first) under a new section describing this as a real, technical enforcement mechanism for the "AI agents work only through software" rule, referencing this 2026-07-26 incident.

## CONSTRAINTS
Do not block read-only gh/git commands (view, checks, log, diff, status, pr list, pr comment, run rerun/view) under any circumstance -- only gh pr merge and git push to a protected branch (master/main) from a non-systemd context. Do not lock out the Owner's own interactive use of gh/git if they SSH in directly -- this guard is about the AI session's own discipline, not about restricting the Owner; if there's no way to distinguish the two given they share the same rajat account, note this honestly as a real limitation rather than silently building something that would also block the Owner.
