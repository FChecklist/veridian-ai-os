## KNOWN_CONTEXT
Real, audit-confirmed findings, do not re-derive. The hierarchical BoQ breakdown-% work and Excel importer are already confirmed solid by the audit (`computeHierarchicalAmount`, circular/missing-parent detection, topological batch insert, RLS, requireAuth() tenant-scoping) -- do NOT touch those, only the valuation/interim-billing piece:
1. **Zero-tax invoices (the real correctness bug)**: `construction-valuation-service.ts`'s `generateInterimBill()` builds invoice line items (billable BoQ lines plus a negative retention-holdback line) that never set `taxTemplateId`, and `erp-invoicing-service.ts`'s `computeInvoiceTotals()` only applies tax when a line explicitly carries a `taxTemplateId` -- there is no company/customer-level fallback. `GenerateInterimBillInput` doesn't even expose a field to supply one. Result: every interim/RA bill generated through this new feature silently posts with zero GST/tax by default -- a real, undisclosed correctness gap for a GST-compliance platform. Not caught by the existing pure-function unit tests (which don't assert on tax fields), and not flagged anywhere in PROGRESS.md.
2. **Retention modeled as a taxable-value reducer, not a holdback**: retention is currently applied as a negative invoice line (`rate: -retentionAmount`), which reduces the invoice's TAXABLE VALUE rather than being a proper payment-term holdback on the invoice total. Once tax is wired in (item 1), this will also understate GST collected by the retention percentage -- fix both together, they compound.
3. **Minor, non-blocking, matches an existing pattern elsewhere** (only fix if trivial, not the priority): interim bill numbering uses `max(billNumber)+1` read-then-insert with no unique constraint on `(projectId, billNumber)` -- a real but pre-existing race-condition class already present in `erpSalesInvoices.invoiceNumber` too, not a new regression introduced by this PR.
